# Native integration acceptance

These tests exercise real HA Core components and APIs, not source-string assertions or fake runtime modules. The main integration fixture loads the actual integration, built-in webhook, native config/options flows, entity/device registries, restoration storage, persistent notifications, frontend module registration and HTTP static bundle. `test_controller.py` covers the real pure controller and sink encoders. No tests have been run by the integration worker.

## Unit/native fixture run

Build `custom_components/ha_tty7/frontend/ha-tty7-card.js` first. The matched environment is Python **3.14**, Home Assistant Core **2026.10.0**, and `pytest-homeassistant-custom-component==0.13.371`. In that isolated environment, with the repository root on `PYTHONPATH`:

```sh
PYTHONPATH=. pytest -v integration-tests
```

The fixture tests use HA's native test loader and HTTP/WebSocket clients. They require no real collector, token, host connection, household configuration or HA service process. This is native behavior/unit evidence, **not HACS download or browser UI acceptance**. A matching test-plugin release must be installed; do not replace HA imports with fake modules if it is unavailable.

The native tests finish the real host/config-entry setup before opening the HTTP test client. That setup loads the actual HTTP/frontend/webhook dependencies and routes. In plugin 0.13.371, `hass_client()` uses the fixture's HA instance implicitly; its optional argument is an access token, not a HA object. `hass_ws_client()` likewise uses its default fixture instance. The plugin isolates automatic HTTP binding/start; aiohttp's test client freezes the app, so all initial host/static route setup must precede client creation. Reloads reuse the registered static route.

## Isolated live UI/API acceptance

Use an authorized disposable Core 2026.10.0 instance with frontend, built-in webhook and persistent notifications available. HACS install/update evidence is owned by the parent. Serve its collector-facing address with verified HTTPS; a URL field alone is not proof of its certificate chain or hostname. The collector must retain TLS verification. No global recorder exclusions, manual frontend resources, host YAML or secrets file is required by this integration.

1. Settings > Devices & services > Add integration > HA-tty7. Fields are `host_id`, `label`, `base_url`, `notify_destination`, `notify_waiting`, `notify_completion`, `dashboard_path`. Start with synthetic `desktop_demo`/`Desktop` and `laptop_demo`/`Laptop`, persistent notifications enabled and `/lovelace/agents` as a local path. Each host requires a different wire ID. The flow rejects HTTP URLs, embedded URL credentials, query/fragment, invalid host IDs and nonlocal dashboard paths. Destination selectors offer only `none`, an installed `persistent_notification.create`, and installed `notify.mobile_app_*` actions.
2. The authenticated `pairing` step contains only the configured host ID and HTTPS webhook URL. Copy the bearer URL privately into collector settings, never chat/screenshots/arguments/logs. Finish the flow before posting. Its random ID is 32 cryptographic bytes represented as 64 hexadecimal characters. Options > Configure shows it again; changing options does not rotate it. Removing the entry revokes it. Readding the same host generates a new credential.
3. Authenticated API equivalents: `POST /api/config/config_entries/flow` with `{"handler":"ha_tty7"}`, then `POST /api/config/config_entries/flow/<flow_id>` with the seven input fields; then submit `{}` to the `pairing` step. Options use `POST /api/config/config_entries/options/flow` with `{"handler":"<entry_id>"}`, submit the six editable fields (no `host_id`), then `{}`. Keep all returned data private because the flow result includes pairing credentials.
4. Discover entity IDs from the actual entity registry, not guessed IDs. Both entries have platform `ha_tty7`, the same per-host `device_id` and `config_entry_id`, unique IDs `<host_id>_roster` / `<host_id>_connectivity`, with descriptions `roster` / `connectivity`. Device identifiers include `["ha_tty7", "<host_id>"]` and its name is the configured label. Modern frontend display entries omit unique IDs; pairing by platform, device identifiers, config entries and exactly one native sensor/binary sensor is supported. Card discovery must exclude other platforms/unconfigured devices.
5. Authenticated state APIs are `/api/states/<entity_id>`. Roster attributes are precisely `schema_version`, `agents`, `counts`, `collector_ok`, `error_code`, `last_contact`, `last_success`, `baseline_ready` plus ordinary HA entity metadata. Confirm there is no secret, webhook URL, base URL or notify destination anywhere in states/device/card data. A new host is `unconfirmed`/connectivity `off`. POST a shared-protocol v1 snapshot privately to its webhook: successful empty means `0`/`on`; nonempty state is the row count; structured error means `error`/`off` while retaining rows. HA receipt time owns timestamps. Check strict malformed UTF-8/JSON, duplicate keys, forbidden fields, over64KiB and wrong host ID: none refreshes contact or alters another host. The built-in webhook policy is POST-only and local-only; HEAD may return 200 without processing, by HA design.
6. Wait for actual silence: after 45 seconds, the next 5-second timer turns healthy **or error** state into `stale`, retaining rows/counts/timestamps/error metadata with baseline false. Startup/reload/restoration remains `unconfirmed` until a new report and must not synthesize alerts.
7. Persistent notifications can be observed through the authenticated WebSocket command `persistent_notification/get`; use increasing request IDs. Test initial done/waiting (no alerts), working-to-waiting, working-to-done, repeated heartbeat (no duplicate), replacement session/pane identity, removed rows, unknown-to-done (no alert), errors/stale/restart/reload reconnect (no replay). Stored roster must already be published when a notification arrives. Existing mobile targets are checked again at delivery. Disable either toggle and confirm it independently. Markdown agent/label text uses padded 65-backtick code spans and flattened CR/LF; mobile text escapes `&<>`. Tags hash the JSON pair of session ID and pane ID and prefix the host ID. No action/command buttons are generated.
8. Reload via `POST /api/config/config_entries/entry/<entry_id>/reload`, inspect unconfirmed restored rows/timestamps, then reconfirm silently. Remove via `DELETE /api/config/config_entries/entry/<entry_id>`; verify entities disappear, old credential cannot update anything, the timer stops, and the bundled extra module is removed after the last loaded host unloads. HA 2026.10 exposes no static-route unregister API; the already-registered public no-host-data bundle route remains and is reused on reload. Its extra-module URL is `/ha_tty7/ha-tty7-card.js?v=0.2.0` and is registered only once across hosts.

Full restart, browser visual-editor rendering, actual HACS download/update, verified TLS collector transport and physical mobile delivery remain distinct runtime evidence gates owned by the parent. Fixture tests do not prove those gates.

## Built-in webhook log privacy

Core 2026.10's webhook component logs bearer IDs on rejected methods, remote-local-only attempts and unknown/revoked routes; at DEBUG it also logs the first 64 bytes of unknown-request bodies. Native HTTP authentication, serving and aiohttp access logs also include webhook URLs. The integration installs the same narrow filter on `homeassistant.components.webhook`, `homeassistant.components.http.auth`, `homeassistant.helpers.http` and `aiohttp.access`: only known project credential digests match for fixed-marker redaction, including IDs embedded in paths/request lines and positional, mapping or already-rendered log messages. HA's actual HTTP request ContextVar scopes the separate webhook raw-body DEBUG line to known project routes. Warnings/errors and exception evidence are retained; unrelated records are unchanged. No tombstone webhook remains registered after unload/removal.

To protect revoked IDs without keeping bearer credentials or unbounded payloads, the process retains only up to 4096 SHA-256 credential digests. Digests are not evicted during the process lifetime. Repeated reloads consume no additional capacity; at the bound, new pairing/registration fails safely with a fixed privacy-capacity message until HA restarts. After restart, only still-configured IDs are known. Removed IDs are no longer usable credentials. This filter does not sanitize external reverse-proxy/access logs or other logging systems; their path-redaction policy remains an independent deployment requirement. `test_native.py` emits actual GET rejection/revoked POST records from all four native loggers and proves unrelated webhook DEBUG records remain visible; `test_log_redaction.py` covers real warning/exception emissions, URL-bearing records with all three formatting styles and the retention bound.
